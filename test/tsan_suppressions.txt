# ThreadSanitizer suppression file for Typesense tests.
# These are pre-existing upstream issues not introduced by our fork.
# Syntax: <type>:<function_or_module_pattern>

# Data race in sparsepp hash map during concurrent batch_memory_index.
# Upstream issue: sparsepp::sparsegroup::_sizing() accessed without
# synchronization from Index::index_field_in_memory() worker threads.
race:spp::sparsegroup*::_sizing

# Lock-order-inversion between two shared_mutex instances in the
# analytics path: SearchAnalytics::add_internal_event() acquires M1
# while holding M0, but other paths acquire in reverse order.
deadlock:SearchAnalytics::add_internal_event

# Lock-order-inversion between Index lock and CollectionManager::get_collection
# shared_mutex. Index::run_search holds the Index lock then calls
# filter_result_iterator_t::validate_object_filter which acquires the
# CollectionManager lock; other paths acquire them in reverse order.
deadlock:CollectionManager::get_collection

# Data race on reference_info map during concurrent collection loading.
# CollectionManager::load loads collections in parallel; add_referenced_ins
# writes to the shared map while load reads from it. Pre-existing upstream
# race in the join/reference loading path.
race:CollectionManager::add_referenced_ins
race:CollectionManager::load_collection

# Lock-order-inversion between Collection shared_mutexes during join/reference
# operations. Collection::search holds one Collection's lock, then various
# reference/join methods (get_reference_filter_ids, get_filter_ids,
# reference_populate_sort_mapping, etc.) acquire another Collection's lock
# in inconsistent order. Broad suppression because the same root cause
# manifests through many different Collection methods.
deadlock:Collection::

# Data races on shared vector<vector<art_leaf*>> in Index methods.
# search_wildcard worker threads read vector::size() while the main thread
# does push_back() in the same function; refresh_schemas/batch_memory_index
# also race on the same vector. Pre-existing upstream synchronization gap.
race:Index::search_wildcard
race:Index::batch_memory_index
race:Index::refresh_schemas

# Data races in RocksDB internals during concurrent reads and writes.
# These are upstream issues in RocksDB's lock-free MemTable (skiplist with
# custom atomics that TSAN cannot fully model) and flush/compaction paths.
# NOT suppressed broadly — only specific internal functions are listed so
# that real synchronization bugs in OUR Store/Collection code are still caught.
#
# MemTable concurrent skiplist (lock-free with custom atomics, TSAN FP):
race:rocksdb::MemTable::Add
race:BytewiseComparatorImpl::Compare
race:rocksdb::Arena::AllocateNewBlock
race:rocksdb::Arena::AllocateAligned
# BlockBuilder vs ZSTD compression during flush (separate buffers, TSAN FP):
race:rocksdb::BlockBuilder::AddWithLastKeyImpl
race:ZSTD_compressBlock
# Internal compaction/flush thread pool races:
race:rocksdb::CompactionJob
race:rocksdb::FlushJob
race:rocksdb::DBImpl::BackgroundFlush
race:rocksdb::DBImpl::BackgroundCompaction
